# Guided Learning Implementation Plan

**Goal:** Upgrade the existing lesson system and pilot the complete P2 Proof chapter before any other chapter rollout.

**Architecture:** Extend existing teach cards additively, preserve lesson and review flows, and use the existing refine pipeline. Introduce a separately configured live learning tutor with guarded question context and verified mathematical output. Deliver a reviewable pilot before upgrading other chapters.

**Tech stack:** Python, Textual, existing tutorlib, JSON packs, FSRS, SymPy, SVG and Obsidian Markdown.

## Global constraints

- Preserve existing learner state, cloud and local model selections and existing lesson behavior when extended content is absent.
- Do not roll out beyond P2-1 until the user approves the completed pilot.
- Do not claim all possible question forms or automated correctness where source coverage or verification cannot support that claim.
- Do not reveal unattempted answers, including via examples, context, model output or diagrams; fail closed when verification is unavailable.
- Preserve source provenance, copyright restrictions and refine no-loss guarantees.

## Work sequence

1. Research official current specifications, P2-1 papers, mark schemes and examiner reports available in the source library, and primary education studies; append evidence strength and limitations to `docs/RESEARCH.md`. Map each pilot form to source evidence and record source gaps.
2. Extend `build/teach_cards.py` additively: short `plain_words`, optional expanded content, `terms` (meaning, notation, spoken form, source), `forms` (wordings, worked example, separate check and answer), `diagrams` references, and misconceptions (temptation and correction). Raise existing field limits thoughtfully; validate nested data and math lint. Keep legacy cards valid while requiring full fields at upgraded chapter gates.
3. Extend existing lesson engine and Textual/Obsidian presentation to stage short content first, expandable depth, terms, examples, diagrams, misconceptions and per-form checks. Review actual SVG renders, including small-terminal fallback. Reuse existing recall scheduling; namespace stable term IDs and migrate without disturbing existing reviews.
4. Add learn model, thinking and effort settings in `app/tutor_app/config.py`, settings and presets without altering existing selections. Use existing AI transports and local preload; build per-idea context in `prompts.py` with history, relevant card and diagram. Implement attempted-state enforcement, deterministic verification of supported calculations with SymPy, and safe fallback for unverified or unsupported mathematics. Adapt misconceptions and schedule revisits using existing profile and review state.
5. Extend foundry drafter and refine roles and gates to validate new content and source coverage; explicitly permit justified diagram exceptions, preserve existing gates and no-loss snapshots. Upgrade only P2-1 via `bin/refine`, not rebuilding its pack.
6. Demonstrate the complete pilot lesson, including terms, examples, form checks, misconceptions, diagrams and live-tutor behavior. Verify terminal and Obsidian output, visually inspect SVGs, run appropriate tests and gates, and report unsupported cases. Stop and request user review before proceeding.
7. Only after approval, upgrade each existing chapter through refine, using source-backed coverage and auditing visual diagrams and limitations. Run all tests and gates, update How It Works, CHANGELOG and STATUS together, and verify terminal and Obsidian displays.

## Review focus

- Existing cards and saved settings remain usable with no migration data loss.
- A current unattempted question cannot leak through model context, prior examples or streaming.
- Unsupported mathematics is not silently presented as verified.
- Term reviews share FSRS scheduling without collisions or changing existing review records.
- A diagram exception records why no appropriate drawable figure exists; source gaps do not become fake completeness.
