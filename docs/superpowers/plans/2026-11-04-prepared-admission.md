# Prepared native Pearson question admission implementation plan

> **For agentic workers:** Use superpowers:subagent-driven-development to implement each named deliverable in order, as the user requested. The coordinator has delegated the choices and will commission separate Standards and Spec review. Keep all changes uncommitted. Steps use checkbox syntax.

**Goal.** Admit a small group of identified native Pearson IAL questions through the normal maker, blind review, immutable registration and additive publication lifecycle, reusing prepared source crops and verified topical occurrences.

**Architecture.** A deterministic preparation command reads pinned Library resources and produces a sealed input package. A separate fresh manager constructor freezes that input, then uses real worker stages. An immutable registration attestation lets the bank authenticate the same assessed group on import and reload using only Library. The current exact pilots retain precedence.

**Tech stack.** Existing Python, AssetLibrary, PyMuPDF/Pillow in the preparation workflow, JSON, manager state locking, CLI, pytest. Keep workflow-only PDF render dependencies out of learner startup.

**Spec.** Workspace file `Work/Workers/extraction/resume-pmt-20261104/prepared-admission-design.md`. Use `stem-tutor/` as the working directory for paths and commands below. One fresh Sol High implementer can take the three task briefs sequentially. No commits, provider launches or production writes during development/tests.

## Global constraints

- Support only current native Pearson IAL structured questions from the twelve installed mathematics courses with a real verified original QP and MS. A PMT occurrence can be an additional witness of the same official item. Unknown, ambiguous, compiled-only, raster-only unidentified cover, wrong-edition and legacy 6691 inputs stay pending. No new learner source kind or AI grading.
- Use physical 1-based pages and normalized rotated CropBox coordinates, exact full-file SHA-256, per-role ordered regions, public/private isolation and part-specific disclosure. At most 100 distinct selected (asset ID, page) pairs per job, including reference, source-identity and shared context. Repeat-use of the same page in parts counts once. Package overhead limits: 1–8 distinct whole Qs on one QP/MS pair per job. An 8-question ceiling is a coordinator design choice, separate from the existing page limit.
- Original-source text/geometry, selection witnesses and crops are proposals. Only the manager-launched independent reviewer can approve the current candidate against every original and the frozen graph. Same-family Codex independence must stay visible. No automatic completion of roles or inference from a COMPLETE marker. Reuse exact verified work, prior immutable revisions and all failure histories.
- The job-local limit is 20% weekly remaining. Controller uses fresh native limit readings with allowance for concurrent usage; no resets, purchases, or changes to global defaults. Never create a fresh job/pass to evade a hold. Tests read via `tests/library_assets.py`, copy inputs into disposable vaults, and keep all worker/candidate outputs disposable.

## Review focus

1. Exchanging PDF roles or a different session/component while editing packet metadata to agree must fail against original bytes and covers (Task 1).
2. Multiple questions sharing a page, cropped rubric notes elsewhere on the page, continuation/blank work pages and reference tables must stay attributed; private content can never enter sibling public views (Tasks 1 and 3).
3. Omitted profile markers or renamed jobs must not bypass exact P1/P2 identity gates, overlapping owners or failure holds (Tasks 2 and 3).
4. Changing a source, seed, assessor graph, private/public raster, worker result or reviewed part-set must invalidate reuse; staged files alone cannot simulate successful stages (Tasks 2 and 3).
5. A concurrent bank switch, duplicated identity, stripped attestation or forged public projection must fail closed without rewriting prior items/history or exposing the rubric (Task 3).
