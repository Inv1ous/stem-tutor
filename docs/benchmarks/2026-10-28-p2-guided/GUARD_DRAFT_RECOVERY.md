# Guard draft recovery: remaining design

A session draft and the durable guard store can diverge. Recovery must not blindly overwrite either. The existing `compare_update` helper checks the full expected guard, updates all copies in one store-file write and treats an already-applied update as success. Cooperating deferred-store writers now share a POSIX file lock. The helper is not integrated into the retry workflow; stale unconditional writes can still overwrite newer drafts.

For integration, persist an operation ID, the full expected store guard and proposed draft in the session before changing the store. Under a lock covering store read, comparison and replacement, apply only against the expected guard. If already applied, continue idempotently. If different, durably retain both complete versions in a conflict record and leave the answer guarded; offer the learner an explicit choice between the drafts. Clear the pending operation and close the retry only after the store update or conflict record is durable. Restart must replay the same operation, never infer intent by blindly copying the session guard. Reject changed protected keys or question instances. An empty draft is a valid intentional edit.

Test interruption before and after every session/store write, duplicate replay, simultaneous writers, changed keys, two consecutive edits, empty drafts, exclusion, replacement and restart. Check that both drafts survive conflict, no answer or rubric leaks, and the chosen draft can actually be recovered. The current helper and unit tests alone do not supply these guarantees.

An attempted integration was removed after review identified two unsafe transitions: cancelling again could overwrite the first proposed draft, and submitting during a conflict could remove its guard while leaving the operation pending. Recovery also needs to distinguish a legitimately resolved guard from a guard missing due to interruption, to prevent resurrection. The eventual UI must preserve edits made while a conflict is unresolved and provide a path to resolve the conflict; merely blocking session end is insufficient. Two strict expected-failure tests capture the interrupted cancellation and competing-edit cases until the complete workflow is implemented.

The experimental `cancel_draft` store primitive is not integrated. Independent review reproduced a guard-generation ABA failure: after resolving and recreating the same guard with identical content, replay of an old operation can falsely report success. It also needs explicit malformed-history validation. A strict expected-failure test records the first issue. Do not connect the primitive to cancellation until guard generation/version is bound to operations and all writers, including resolve/recreate, are covered.
